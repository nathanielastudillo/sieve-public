## Headline outcome

Orchestrator saw zero successful members across 6 generations. But
Redis shows **10 successful training results with real val_losses
(3.85 – 4.26)**, well below log(V)=8.987 — i.e. individual members
were training correctly. The orchestrator and the workers disagreed
about whether anything succeeded.

## The two root causes

### Cause 1 (primary, this-run blocker): generation timeout too short

```
orchestrator.py:731   "job_timeout_s": 7200.0,   # 2 hours
```

Actual per-member wallclocks on corpus_v009 (from Redis `wallclock_s`
field):

|---|---|---|---|

| 54aefb8f (gen 0) | ok  | 10.77h | node-6 |
| 54b33369 (gen 0) | ok  |  5.02h | node-10 |
| 6031cb4d (gen 0) | ok  |  6.39h | node-4 |
| 92664c6c (gen 0) | ok  |  6.30h | node-7 |

| cabccbca (gen 1) | ok  |  9.83h | <node-ip> (standalone) |
| c5899d68 (gen 3) | ok  |  6.61h | node-10 |

Training takes 5 – 11 hours per member. The orchestrator gave 2 hours
per generation, then timed out all 8 members with `status=error,
error="timeout"` (`dispatch.py:178-185`), and advanced to the next
generation. Meanwhile the workers kept training and published their
late results to `sieve:results:...:gen:member` — keys the orchestrator
had already stopped polling.

Consequence: every evolutionary step operated on an all-inf
population, so reproduction was effectively random re-sampling with
no selection pressure. The cluster burned ~170 GPU-hours on
un-selectable work.

### Cause 2 (secondary): CUDA OOM on two standalones

Two standalones — `<node-ip>` (<standalone>-9dba) and `<node-ip>`
(<standalone>-ad3f) — OOM on job intake:

- 29 of 48 enqueued jobs errored on these two nodes alone
- They consume a job, fail in ~milliseconds, BLPOP the next one — so
  at every generation boundary they burn through the queue before
  slower-but-working nodes can pick up jobs
- Root cause not yet investigated. Both were in the
  `fit_fitz_on_standalones.sh` list so pymupdf is fine; this is GPU
  memory. Possible causes: residual processes, smaller free VRAM
  than peers, different kernel/driver state

### Non-cause: rsync SSH user mismatch (defensive fix applied anyway)

While diagnosing I initially attributed the `inf` to rsync failure in
`dispatch_training_redis` — the orchestrator pulls checkpoints back
from workers via `... rsync {node}:...` with no user prefix,
so compute worker_ids like `node-9-1868887` would attempt to ssh as the
orchestrator's local user, not `a`. In fact this path was never
reached for exp007_v009 because every member hit the timeout branch
at `dispatch_training_redis:486-490` before the rsync stage.

The fix is still valid hardening and has been applied
(`controller/orchestrator.py`):

- New `--ssh-user` / `--ssh-pass` CLI flags + env fallback, threaded
  into `_dispatch_cfg` as `ssh_user` / `ssh_pass` (default `a` /
  `$SSH_PASS`)
- Rsync target now `{ssh_user}@{node}:{remote_path}`, with a bypass
  (`if "@" in node`) for standalone worker_ids like
  `a@<node-ip>-21552` which already encode the user
- On rsync failure the member's `val_loss` is no longer clobbered back
  to `inf`; only `checkpoint_path` is cleared. This lets
  `best_individual` report correctly even when we fail to retrieve
  the checkpoint

## Lessons applied to next run

1. **`job_timeout_s` must track corpus size.** For v009 at current
   model size (~7M params, epochs≈6, batch≈64), set it to ≥ 36000s
   (10h) with a generous margin. Long-term, expose it as a CLI flag
   (currently hardcoded in `orchestrator.py:731`).
2. **Make timeouts per-member, not per-generation.** Generation-level
   deadline punishes the whole cohort for one slow node. Dispatcher
   already wakes per-member; this is a small refactor to compute a
   per-job deadline and keep collecting late arrivals up to a
   global ceiling.
3. **Exclude .116 and .152** from the standalone pool until OOM is
   investigated — one-off CUDA check in `deploy_sieve_daemons.sh`
   would catch this. The candidate list at `/tmp/standalone_candidates.txt`
   should be pruned.
4. **Reclaim the exp007 checkpoints** before killing the run dir —
   at a minimum pull all 10 ok checkpoints to
   `runs/exp007_v009/checkpoints/` locally and run a standalone
   ensemble eval. They're strong individuals and the first real data
   point on v009.
